# مراجعة الهيكلة — 2026-10-07

أرقام مقاسة من الكود (الباك‑إند `testing` + تطبيق `bim_app`)، مرتّبة بالأولوية. كل بند: **المشكلة ← الدليل ← الحل المقترح ← المخاطرة**.

## ما هو سليم (لا يُلمس)
- v1 اتشال بالكامل، والـ API كله v2 موحّد (`routes/api_v2.php`، 592 مسار).
- بوابة واحدة لكتابة إعدادات الخدمات (`ChildServiceWriter`)، ومصدر واحد لشروط المتجر (`option_user`).
- طبقة خدمات موجودة (158 ملف) وتغطية اختبارات للباك‑إند (3420 اختبار نجح).

## 1) بيانات التصنيفات (taxonomy) تعيش داخل الـ Seeders — الأولوية الأولى
- **الدليل:** 226 seeder / 119 ألف سطر، منها 77 ملف بيانات / 95 ألف سطر؛ `DatabaseSeeder` بينادي 92 خطوة. القرارات (مجموعات خيارات، تجريد، ربط خدمات) مكتوبة كشيفرة تُعاد تشغيلها.
- **العَرَض الفعلي:** 45 اختبار كانوا فاشلين لأنهم بيقيسوا «لقطة تاريخية» لحاجات انت قلّصتها. و`TradeVocabularySeeder` كان بيعيد إنشاء مجموعة محذوفة في كل تشغيل. أي seeder إضافي-فقط بيرجّع اللي اتحذف يدويًا.
- **الحل:** مصدر حقيقة واحد = لقطة تصنيفات مُصدَّرة ومُرقّمة (JSON/SQL) + جدول سجل تغييرات (`taxonomy_changes`). الـ seeders القديمة تتجمّد كأرشيف ولا تُشغَّل. أي تعديل جديد = migration بيانات صغيرة بتاريخ.
- **المخاطرة:** متوسطة. تتم على مراحل: أولًا تصدير اللقطة والتحقق إن إعادة بنائها = قاعدة الإنتاج، وبعدها نوقف الـ seeders.

## 2) الاختبارات معتمدة على قاعدة بيانات التطوير نفسها
- **الدليل:** 423 اختبار بـ`DatabaseTransactions` على بيانات حقيقية، وfactory واحدة فقط. الـsuite 8–10 دقائق، ولما أضفنا بوابة التسليم فشل ~50 اختبار بسبب بيانات ناقصة.
- **الحل:** (أ) قاعدة اختبار صغيرة مُحكمة (dump مُجمّد + factories للكيانات الأساسية) وتشغيل `--parallel`. (ب) فصل اختبارات «سلامة التصنيفات على البيانات الحقيقية» في مجموعة منفصلة تُشغَّل عند الطلب.
- **المخاطرة:** منخفضة، لأن الاختبارات القائمة تبقى. الفايدة: سرعة 3–4×، وإنها تفشل لسبب حقيقي فقط.

## 3) ملفات ضخمة ووصول مباشر للبيانات داخل الـ controllers
- **الدليل:** 90 استدعاء `DB::table` في 22 من 100 controller بـApi/V2، و191 في AdminV2، و168 في Services. أكبر الملفات: `ServiceExecutionEngine` 1887 سطر، `AdminV2/BookingController` 1597، `CustomerCartService` 1499، `BusinessMenuItemController` 1431، `DisputeService` 1194.
- **الحل:** استخراج «Query objects/Actions» لأكبر 6 ملفات بدون تغيير سلوك، والاختبارات الحالية هي شبكة الأمان. القاعدة: الـcontroller يتحقق ويستدعي، والخدمة تقرر، والـquery object يقرأ.
- **المخاطرة:** متوسطة، تُنفَّذ ملفًا ملفًا.

## 4) بقايا قديمة
- **الدليل:** `app/Libraries/Main.php` (1491 سطر، 35 دالة، 4 مستخدمين فقط)، `PushNotification.php`، وإشارات لـ`Api\V1` داخل `PostAudienceService`.
- **الحل:** حصر الدوال المستخدمة فعليًا ونقلها لمساعدات صغيرة، ثم حذف الملف.
- **المخاطرة:** منخفضة.

## 5) التطبيق: شاشات عملاقة وحالة داخل الواجهة
- **الدليل:** 14 شاشة فوق 700 سطر (`tech_pricing_screen` 1815، `menu_items_screen` 1628، `menu_item_edit_screen` 1430، `orders_and_bookings_screen` 1396، `retail_listings_screen` 1301). 71 شاشة بتنادي الـ API مباشرة من `ConsumerStatefulWidget` بدل controller، وفيتشر `business_menu` لوحده 8.4 ألف سطر. نموذج الصنف موجود في فيتشرين (`business` و`business_menu`)، وفيه محرّران لنفس الصنف (التسعير والتفاصيل / النموذج الكامل).
- **الحل:** تقطيع الشاشات الكبيرة لأقسام وويدجتس + controller لكل شاشة (نبدأ بـ`tech_pricing` و`menu_items`)، ودمج نموذجي الصنف في واحد، وتوحيد المحرّر.
- **المخاطرة:** متوسطة، والحماية: اختبارات الواجهة (56 ملف حاليًا لـ518 ملف كود).

## 6) غياب عقد API مختبر
- **الدليل:** `docs/api/openapi-v2.yaml` موجود لكن لا شيء يتأكد إن شكل الردود (Resources) يطابقه، والتطبيق بيقرأ JSON يدويًا (`fromJson`).
- **الحل:** اختبار عقد: لكل endpoint رئيسي، يقارن مفاتيح الرد بالـ OpenAPI، ويفشل لو اتغيّر شكل بدون توثيق. (كان سيمنع أخطاء مثل `remove=true`.)

## 7) تشغيل وبيئة
- **الدليل:** أخطاء متقطعة `Access denied for user 'forge'` في السجل (إعدادات `.env` بتُحمَّل أحيانًا من غير كلمة المرور تحت Apache، وبـ`APP_ENV=production` تارة و`local` تارة).
- **الحل:** مراجعة تحميل `.env` وcache الإعدادات في XAMPP، وتوحيد البيئة بين `artisan serve` وApache.
