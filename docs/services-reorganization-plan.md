# خطة عمل: إعادة تنظيم الخدمات لكل بزنس

**الحالة:** مسودة للمراجعة — لم يبدأ أي تنفيذ بعد. مُعدّة نهاية جلسة 2026-09-23 استعدادًا لجلسة قادمة.

**طلب المالك (نصًا، ملخّصًا):**
> فى بداية الجلسة القادمة هنعيد تنظيم الخدمات لكل بزنس من جديد. هنفتح مثلاً
> الأب "سياحة وفنادق" ونحدد مجموعة ليها نفس الخيارات، ونعمل customize للخدمة
> بشكل منظم لهذه المجموعة. وبعدها هذه الخدمات هى اللى تظهر فى "إدارة خدماتى"
> فقط، مع الإعدادات العامة لأى بزنس (فرق العمل، مواعيد العمل، التحقق من
> الحضور، إلخ). وإعادة صياغة خدمات الصحة الرئيسية وطرق البحث.

---

## ١. الآلية الموجودة بالفعل — لسنا بادئين من صفر

قبل اقتراح أي حاجة جديدة، هذا اللي موجود ومُختبر بالفعل ويمكن البناء عليه:

| الطبقة | الجدول/الملف | الوظيفة |
|---|---|---|
| هل الفرع يقدّم الخدمة؟ | `category_platform_services` | ربط (child, service) on/off |
| كيف تتصرف الخدمة لهذا الفرع؟ | `category_service_config` (`CategoryServiceConfig`) | JSON: `allowed_item_types`، أنماط الحجز، إلخ |
| **مجموعات فرعية داخل خدمة واحدة ("Branches")** | `platform_service_item_groups` + `group_id` على `platform_service_item_types` | **هذه أقرب آلية موجودة لمفهوم "مجموعة ليها نفس الخيارات"** — مثال: تحت خدمة `booking` فيه فروع (hotel / clinic / sports / restaurant_table / training) |
| السعر لكل (بزنس، نوع عنصر) | `business_service_prices` | مصدر السعر الوحيد |
| خصائص وصفية للنشاط | `category_child_option` + `option_groups.price_role` | `line` = يُسعَّر، `modifier` = يُغيّر سعر، `descriptive` = وصف فقط |
| نطاق صاحب البزنس (owner-only) | `ResolvesOwnerCatalog` trait | `servicesForChild()` / `allowedTypesByService()` / `assertAllowed()` — نفس المنطق مستخدم فى v2 API الحالي |

**الخلاصة:** `platform_service_item_groups` هو بالظبط المكان اللي "التجميع + التخصيص" لازم يحصل فيه — لكنه مبني حاليًا كأداة أدمن (AdminV2) بمنطق عام لكل الخدمات، مش بمنطق "افتح الأب، حدد مجموعة فرعية، اعمل لها شاشة تخصيص خاصة ومنظمة" اللي طلبه المالك. الفجوة مش فى الجدول، الفجوة فى تجربة الإدارة والعرض.

## ٢. واقع البيانات الحالي — التجميع تلقائيًا حسب "بصمة الخدمات"

فحصت كل ٢٠٥ فرع (child) عبر الـ ٢١ جذرًا الحية، وجمّعتهم حسب مجموعة الخدمات النشطة لكل واحد. النتيجة ١٩ "بصمة" مختلفة، أكبرها:

| العدد | الخدمات | أمثلة حقيقية |
|---|---|---|
| ٦٦ | `booking + business_offers` | فندق، شقق فندقية، منتجع، نجار تنده، فني تكييف، بلياردو، محاسبة |
| ٣٨ | `booking + business_offers + delivery + menu + retail` | أكسسوار، ألومنيال، قطع غيار سيارات، أدوات نجارة (سلع تحتاج حجز معاينة/تركيب + توصيل) |
| ٢٩ | `business_offers + delivery + menu + retail` | مخابز، كتب، اسمنت، بن، ستائر وديكور — محلات سلع بدون حجز |
| ١٢ | `booking + business_offers + menu` | دعاية وإعلان، تنسيق حفلات، مقاولات، بلاي ستيشن |
| ١٠ | `booking + business_offers + delivery + menu` | **مطعم**، كافيه، عربية قهوة، مجمع مطاعم، أكل بيتي |
| ٨ | `booking + business_offers + delivery + retail` | نجف، مواد غذائية ومنظفات، رخام وجرانيت، مواد دوائية |
| ٨ | `business_offers + delivery + menu` | معدات زراعية، أعلاف، مزارع سمكية |
| ٨ | `booking + business_offers + training` | جيم، نادي رياضي، أكاديمية رياضية، مدرب |
| ٥ | `booking` فقط | اتصالات، برمجة، مراكز أشعة، مركز حجامة |
| ٤ | `booking + business_offers + schedules` | سائق، ليموزين، نقل ركاب |
| باقي (٧ بصمات) | تركيبات فردية | كل واحدة ١-٤ فروع فقط |

**نقطة مهمة تؤكد كلام المالك بالظبط:** "مطعم" له بصمة (`booking+delivery+menu`، بدون `retail`) مختلفة تمامًا عن الصيدلية والسوبر ماركت. لكن لاحظ إن أدوات السلع العامة (٣٨+٢٩+٨ = ٧٥ فرع) بتستخدم `menu`/`retail` بنفس الطريقة تقريبًا لبيع سلعة — والفرق الحقيقي بينهم هو **الحجز** (booking) مش نظام المنيو نفسه. يعني "الصيدلية" و"السوبر ماركت" فى نفس منطق البيع (menu/retail/delivery) لكن المطعم مختلف لأنه بيضيف الحجز فوقهم (طاولة/معاينة).

## ٣. مجموعة الصحة — حالة خاصة، لا تتطابق مع بعضها إطلاقًا

فحصت الـ ٧ فروع تحت "الصحة" (٢٠) بمفردهم — **كل فرع له بصمة مختلفة عن التاني**:

| الفرع | الخدمات الحالية |
|---|---|
| صيدلية | `booking + menu` |
| عيادة | `booking + business_offers + training` |
| مراكز أشعة | `booking` فقط |
| مركز حجامة | `booking` فقط |
| مركز طبي | `booking + training` |
| مستشفى | `booking + training` |
| معمل تحاليل | `booking + business_offers` |

هذا يتوافق مع اللي اتقال فى جلسة سابقة (سطر التسعير الوصفي مقابل السطر المسعر للتخصصات، وفرق العيادة عن المستشفى فى آلية التسعير). لازم "إعادة صياغة خدمات الصحة" تاخد بالها إن:
- **صيدلية** فعليًا محل سلع (منطقها أقرب لـ retail/menu مش booking) — هل الـ`booking` عليها فعلاً مستخدم؟ محتاج تأكيد.
- **عيادة/مستشفى/مركز طبي** الثلاثة دول عندهم منطق تسعير مختلف اتفق عليه فعلاً (عيادة = سعر موحّد للطبيب، مستشفى = سعر لكل طبيب ولكل موعد تحدده الإدارة — لسه مش مبني، هو "جدول تواجد الأطباء" فيز ٢ المؤجلة).
- **مراكز أشعة / مركز حجامة / معمل تحاليل** كلهم خدمة واحدة تُحجز وتُسعّر، بدون التعقيد الطبي للتخصصات — ممكن يبقوا نموذج مبسّط واحد.

## ٤. المقترح: ثلاث طبقات، لا طبقة واحدة

بدل تصنيف واحد "مجموعة" يحاول يغطي كل حاجة، أقترح تقسيم الموضوع لثلاث أسئلة منفصلة (كل واحدة منها قرار مختلف):

### أ) "نمط التعامل" (Handling Pattern) — يحدد شكل شاشة "خدماتى" وواجهة العميل
مُشتق مباشرة من بصمة الخدمات (القسم ٢). مرشح مبدئي لعدد صغير من الأنماط المفهومة بدل ١٩ بصمة:

1. **حجز خدمة/وقت بدون سلعة** (`booking` وحده أو + `business_offers`) — الأغلبية الساحقة (٦٦+).
2. **مطعم/مقهى** (`booking+delivery+menu`, بدون retail) — طاولة + طلب أكل، فاتورة موحدة (موجود بالفعل فى `services-blueprint.md`).
3. **محل سلع (بدون حجز)** (`business_offers+delivery+menu+retail` أو تركيباتها) — الصيدلية والسوبر ماركت والمخبز هنا منطقيًا.
4. **سلعة تحتاج معاينة/تركيب** (تشمل booking فوق menu/retail) — أدوات نجارة، ألومنيال، تكييف.
5. **تدريب/برامج متابعة** (`training`) — جيم، أكاديمية، مدرب.
6. **نقل وخطوط سير** (`schedules`) — سائق، ليموزين.
7. **الصحة كنمط مستقل** — لا يندرج تحت أي مما سبق بسبب التخصصات والتسعير الطبي الخاص.

### ب) "التخصيص داخل النمط" (Customization) — الخيارات الفعلية لكل فرع
هنا فين `platform_service_item_groups` (الـ Branches) و`category_service_config.allowed_item_types` بيشتغلوا فعلاً. المطلوب مش جدول جديد — المطلوب **شاشة إدارية** (أدمن أو ربما شاشة فى `/business`) تفتح جذرًا، تختار الفروع اللي هتتعامل كمجموعة واحدة، وتحرر خياراتها المشتركة فى مكان واحد بدل ما تتفرق على شاشات الفرع الواحد.

### ج) "الإعدادات العامة" — لا علاقة لها بالخدمة نفسها
المالك سمّاها صراحة: فرق العمل (staff)، مواعيد العمل (working hours)، التحقق من الحضور (attendance). دول موجودين بالفعل كميزات منفصلة (Staff delegation، Business working hours، Staff attendance) — المطلوب مش بناء، المطلوب **فصلهم فى الواجهة** عن قائمة "خدماتى" بدل ما يتلخبطوا مع بعض.

## ٥. "إدارة خدماتى" — إعادة التصميم المقترحة

الوضع الحالي (bim_app): تبويب "خدماتى" يعرض بلاطات الخدمات المُفلترة حسب فئة البزنس (المذكرة: service redistribution — تم لكل الـ٢١ جذرًا). المطلوب الجديد:

```
خدماتى
 ├─ [الخدمات المُخصّصة للفرع] ← من (أ) + (ب) أعلاه، منظمة حسب نمط التعامل
 │    مثال لمطعم: المنيو، الطاولات/الحجز، طلبات التوصيل
 │    مثال لعيادة: تخصصاتى، مواعيد الكشف، الدور/QR
 └─ [الإعدادات العامة] ← قسم منفصل تمامًا
      فرق العمل، مواعيد العمل، التحقق من الحضور، الأسعار العامة (إن وُجدت)
```

هذا يعني تعديل شاشة "خدماتى" الحالية فى bim_app لتفصل القسمين بصريًا (مش بالضرورة API جديد — الفلترة الحالية بالفعل موجودة، الشغل هنا فى العرض + إضافة قسم الإعدادات العامة اللي مش معروض حاليًا كقسم موحّد).

## ٦. قرارات محتاجة تأكيد من المالك قبل البدء

هذه فروقات لو اتفق عليها الأول هتوفر وقت كتير أول الجلسة:

1. **مستوى التجميع:** هل "المجموعة" دايمًا فروع تحت نفس الجذر (زي سياحة وفنادق)، ولا ممكن تعدي جذور (مثلاً كل محلات السلع من جذور مختلفة فى مجموعة واحدة)؟ القسم ٢ بيقترح إن التطابق فعليًا بيحصل عبر الجذور مش بس جواها.
2. **مين يملك شاشة التخصيص:** أدمن فقط (AdminV2، زي باقي التاكسونومي)، ولا صاحب البزنس نفسه يقدر يخصص جزء بسيط (زي أسماء الأقسام) من `/business` أو bim_app؟
3. **الصيدلية تحديدًا:** هل تفضل تفضل جزء من "الصحة" (بمنطقها الطبي) ولا تتحول لنمط "محل سلع" بالكامل زي ما بصمتها الحالية (`booking+menu`) توحي؟
4. **هل نمط "سلعة تحتاج معاينة/تركيب"** (٣٨ فرع) فعلاً محتاج يبقى نمط مستقل، ولا يُدمج مع "محل سلع" العادي والفرق بس إن الحجز اختياري؟

---

## ٧. ترتيب تنفيذ مقترح (بعد تأكيد القرارات)

1. تثبيت تسمية الأنماط (القسم ٤-أ) كقائمة نهائية مُتفق عليها.
2. شاشة أدمن واحدة: افتح جذر → اختار الفروع اللي هتتجمع → حرر الخيارات المشتركة (بناء فوق `platform_service_item_groups`/`category_service_config` الموجودين، مش استبدالهم).
3. تطبيق النمط على "سياحة وفنادق" كمثال حي وتحقق كامل قبل التعميم.
4. تعديل شاشة "خدماتى" فى bim_app: فصل الخدمات المخصصة عن الإعدادات العامة.
5. إعادة صياغة فروع "الصحة" فرعًا فرعًا حسب القسم ٣، مع مراعاة الشغل الحالي (التخصص الوصفي، أسعار العيادة المبسطة، الدور).
6. مراجعة/تحديث طرق البحث فى الصحة (discovery) لتعكس التصنيف الجديد.

## ٨. إضافة: الماركات — نظام مزدوج مكتشف، محتاج قرار دمج

فى نفس اليوم، اتسأل: هل نستغنى عن "ماركات الأجهزة الكهربائية" (مجموعة خيارات modifier يدوية، ١١ ماركة فقط) لصالح `catalog_manufacturers`/`catalog_brands`؟

**الاكتشاف:** النظامان موجودان بالفعل ومتوازيان لنفس الفرع (٨٨ — أجهزة كهربائية):

| | مجموعة الخيارات (menu) | Catalog (retail) |
|---|---|---|
| عدد الماركات | ١١ يدوية | `catalog_brands` = ٣٣٧ عالميًا، `catalog_manufacturers` = ٢٧١ |
| الربط بالمنتج | modifier على صنف المنيو | `catalog_products.brand_id` + `manufacturer_id` — عمود حقيقي على كل منتج |
| التغطية الفعلية للفرع ٨٨ | — | خدمة `retail` مفعّلة بالفعل ومقيّدة لـ`home_appliances`+`appliance_spare_parts`، و٣٦ منتج حقيقي بـ١١ ماركة مختلفة موجودين فعلاً |
| كريازي/تورنيدو/LG/توشيبا العربي | كلهم موجودين (بأسماء متطابقة تقريبًا) | نفسهم موجودين فى `catalog_brands` بالفعل |

**يعني:** الفرع ٨٨ عنده بالفعل قناة بيع كاملة وشغالة (retail + catalog_products) بمنطق ماركة/تصنيف أدق وأشمل من مجموعة الخيارات القديمة. هذا مثال حي إضافي على "نمط التعامل" المختلف بين محل سلع (retail/catalog) ومنيو (menu/option-groups) المذكور فى القسم ٤ — وربما يحسم قرار #٤ فى القسم ٦: **أجهزة كهربائية تحديدًا يجب أن تكون retail بالكامل، لا menu**.

**قرار مُرجّأ لجلسة إعادة التنظيم:** هل نُلغي "ماركات الأجهزة الكهربائية" (والمجموعات المشابهة اليدوية لماركات أخرى، لو وُجدت) ونحوّل الأعمال المشابهة (أجهزة كهربائية وما شابه) لتعتمد كليًا على `catalog_products`/`retail`، أم نُبقي المسارين لأسباب انتقالية؟ هذا القرار يمس ملف تعديل ماركات السيارات كمان (نفس النمط: modifier يدوي بينما `catalog_manufacturers` غالبًا أشمل).
